# ReflectX Health — Provider Dashboard for Reflect XR & Reflect Mobile

**ReflectX Health** is a provider dashboard prototype built for Persistent Technology Inc. (PTI) by a four-person GMU Challenge X team. Therapists use it to follow how their clients engage with **Reflect XR** (immersive VR art therapy) and **Reflect Mobile** (creative reflection app), review mood trends, keep session notes, and track Remote Therapeutic Monitoring (RTM) time. A role-aware AI assistant answers questions about the provider's own data. All data is synthetic.

---

## ✨ Features

- **🔐 Centered Auth Portal**: Login (username or email) and Signup screens with JWT-based sessions and role-based routing (Provider vs Admin).
- **📋 Provider Patient List**: Searchable table of a provider's assigned clients with diagnosis, status (`Active`, `Chronic`, `Resolved`) and filtering.
- **🧠 Patient Detail**:
  - Demographics, assigned providers and diagnosis history.
  - Therapy sessions (remote or in person) and provider notes / trend logs.
  - Reflect XR and Reflect Mobile app usage, with session length and module.
- **👤 My Profile**: A provider's own profile and assigned patients.
- **🛡️ Admin Views**: Provider list and provider detail pages with assigned-patient counts.
- **🤖 AI Chat Widget**: Floating, role-aware assistant that answers only from the logged-in user's permitted data. Runs on a local Ollama model by default, so records are not sent to a hosted provider.
- **🎨 Reflect XR Design System**: Plus Jakarta Sans, ambient glow background, sunset color scheme (`#f43f5e`, `#ec4899`, `#a855f7`), floating pill navigation, color-coded status badges.

---

## 🛠️ Tech Stack

- **Frontend**: React 18, Vite 5, React Router DOM v7, Vanilla CSS3 with CSS variables, Lucide React
- **Backend**: Python / FastAPI, JWT authentication (`backend/`)
- **AI**: Local Ollama (`qwen3:4b`) with role-scoped database access
- **Database**: PostgreSQL 16 (synthetic data only)
- **Synthetic data**: Patient demographics generated with [Synthea](https://github.com/synthetichealth/synthea); diagnoses, medications, notes, app usage and RTM data are generated by scripts in `database/`

## 🚦 Getting Started

### 1. Prerequisites
- **Node.js**: `v20.17.0+` or `v22+` recommended
- **npm**: `v10+`
- **Python**: 3.11+ (for the backend)
- **PostgreSQL**: `v16` (see the Database section)

### 2. Installation & Setup
Clone the repository and install the frontend dependencies:

```bash
git clone https://github.com/Asaini434/PersistentPals.git
cd PersistentPals/frontend
npm install
```

### 3. Environment Configuration
Copy `.env.example` to `.env` and set your backend API URL if connecting to a server:

```bash
cp .env.example .env
```

Default environment variable:
```env
VITE_API_URL=http://localhost:8000
```

### 4. Build the database
Do this before starting the backend. See the **Database** section below.

### 5. Run the FastAPI backend

The API authenticates against `users` and `user_credentials` in PostgreSQL. Passwords are verified against the bcrypt-compatible hashes created by `database/seed.sql`.

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn main:app --reload --port 8000
```

Set `DATABASE_URL` and replace `JWT_SECRET` in `backend/.env`. The chatbot is configured to use Ollama locally with `qwen3:4b`, so it does not need Hugging Face credits or send records to a hosted model provider. Install Ollama from [ollama.com/download](https://ollama.com/download), then download the model with `ollama pull qwen3:4b`. Keep Ollama running while using the chatbot. Change `CHATBOT_PROVIDER` to `huggingface` only if you want to use a hosted model; hosted inference requires an HF token and `CHATBOT_ALLOW_EXTERNAL_PHI=true`.

### 6. Test authentication

1. Start PostgreSQL and make sure the `reflect` database has been built (see Database section).
2. In `backend/`, create `.env` from `.env.example`, set a working `DATABASE_URL`, and replace `JWT_SECRET` with a long random value.
3. Install the backend packages with `pip install -r requirements.txt`, then start the API. Confirm `http://localhost:8000/health` returns `{"status":"ok"}`.
4. Open the interactive docs at `http://localhost:8000/docs`, or use Postman, and send `POST /auth/login` with `{ "username": "sjenkins", "password": "demo-password" }`. A successful response is HTTP 200 with `user` and `access_token` fields.
5. Send `GET /auth/me` with `Authorization: Bearer <access_token>` to confirm the token works. A wrong password returns HTTP 401.

### Backend API routes

API handlers are grouped under `backend/routes/`. Login accepts either a seeded username or email and returns an eight-hour bearer token. Send that token in `Authorization: Bearer <access_token>` for protected routes.

| Method | Endpoint | Access | Purpose |
| :--- | :--- | :--- | :--- |
| `GET` | `/health` | Public | Health check. |
| `POST` | `/auth/login` | Public | Authenticate with `{ "username": "sjenkins", "password": "demo-password" }`; `email` is also accepted. |
| `GET` | `/auth/me` | Authenticated | Verify the bearer token and return the logged-in user id and role. |
| `GET` | `/logs/patient-list` | Provider/Admin | List the caller's assigned patients. Admins may pass `?providerId=<uuid>`. |
| `GET` | `/providers/{provider_id}/patients` | Provider/Admin | List a provider's assigned patients; providers can only request themselves. |
| `GET` | `/providers?providerId=<uuid>` | Provider/Admin | Get a provider profile and assigned patients; providers can only request themselves. |
| `GET` | `/patients/{patient_id}` | Provider/Admin | Get patient demographics, assigned providers, diagnosis history, notes, app sessions, and therapy sessions. |
| `GET` | `/admin/providers` | Admin | List provider accounts and assigned-patient counts. |
| `GET` | `/admin/providers/{provider_id}` | Admin | Get one provider and assigned-patient details. |
| `GET` | `/chat/messages` | Provider/Admin | Recent chat history for the logged-in user. |
| `POST` | `/chat/messages` | Provider/Admin | Send a message to the AI assistant and receive its reply. |
| `DELETE` | `/chat/messages` | Provider/Admin | Clear the logged-in user's chat history (soft delete). |

The schema does not currently store provider addresses or licensing metadata, so the APIs do not fabricate those fields.

## 🗄️ Database (PostgreSQL)

The database holds **synthetic data only** (no real patient information). Patient names, birth dates and genders come from Synthea; diagnoses, medications, therapy notes, app usage, mood scores and RTM records are generated by the scripts in `database/seed/`.

### 1. Prerequisites
- **PostgreSQL**: `v16` recommended

**macOS (Homebrew):**

```bash
brew install postgresql@16
brew services start postgresql@16
```

If `psql` is not found afterward, add Postgres to your PATH using the `export PATH=...` line Homebrew prints after install.

**Alternative (Docker):**

```bash
docker run --name reflect-db -e POSTGRES_PASSWORD=devpassword -e POSTGRES_DB=reflect -p 5432:5432 -d postgres:16
```

### 2. Create the Database

Only needed the first time on your machine. If it says `already exists`, you can skip it.

```bash
createdb reflect
```

### 3. Build the Tables and Load Sample Data
From the repository root, one command builds everything. It is safe to rerun.

```bash
./database/run_all.sh reflect
```

The script runs these files in order (you can also run them yourself with `psql reflect -f <file>`; this is the route for Windows without Git Bash):

1. `database/schema.sql`
2. `database/seed.sql`
3. `database/seed/load_patients.sql`
4. `database/seed/seed_therapy.sql`
5. `database/seed/seed_engagement.sql`
6. `database/seed/seed_clinical.sql`
7. `database/seed/seed_rtm.sql`

With Docker, pipe each file through the container, for example:

```bash
docker exec -i reflect-db psql -U postgres -d reflect < database/schema.sql
```

If your database still has the earlier hospital-themed demo patients (Eleanor Vance, Marcus Brody, Sophia Patel, Arthur Pendelton), run `database/maintenance/cleanup_old_demo.sql` once. If it fails on a leftover table such as `patient_communications`, delete that table's rows for those patients first, or ask Ananya.

### 4. Verify

```bash
psql reflect
\dt
\q
```

You should see the tables listed below.

### 5. Reset from Scratch

```bash
dropdb reflect
createdb reflect
./database/run_all.sh reflect
```

Connection string for the API: `postgresql://localhost:5432/reflect` (Docker: `postgresql://postgres:devpassword@localhost:5432/reflect`).

### Tables

| Table | Purpose |
| :--- | :--- |
| `users` | Provider and admin accounts (role `Admin` or `Provider`) |
| `user_credentials` | Usernames and bcrypt password hashes for logins |
| `patients` | Patient demographics (synthetic) |
| `assignments` | Which provider is assigned to which patient |
| `patient_medical_history` | Diagnoses, with severity, onset date and treatment start date |
| `patient_medications` | Medications per patient (name, dose, frequency, status) |
| `clinical_sessions` | Therapy sessions between provider and patient (remote or in person) |
| `modules` | Catalog of Reflect XR and Reflect Mobile experiences |
| `sessions` | Patient app usage: module, start and end time |
| `response_entries` | Self-reported mood scores (1 low to 5 high) tied to app sessions |
| `rtm_enrollments` | RTM enrollment and consent per patient |
| `rtm_activities` | Provider reviews, communications and management time (RTM billing minutes) |
| `rtm_documentation` | Documentation status per 30-day RTM period |
| `provider_notes` | Therapy session notes and trend logs |
| `chat_messages` | AI chat history |
| `audit_log` | Append-only trail of who viewed or changed what |

### Conventions
- Every table has `id` (UUID), `date_created`, `is_deleted`, and `date_deleted`, following PTI's tech spec (`audit_log` is append-only and has no soft delete).
- Timestamps are stored in UTC (`timestamptz`) and converted for display only.
- Rows are soft-deleted (`is_deleted = true`) in normal operation. The one-off `maintenance/cleanup_old_demo.sql` hard-deletes fake demo rows.
- No nullable text columns: use an empty string instead.
- Durations are computed from start and end times, not stored.
- Schema changes are made with `ALTER TABLE` / `CREATE TABLE IF NOT EXISTS` so existing data is never dropped.
- All data is synthetic. Never commit real patient data or credentials.
